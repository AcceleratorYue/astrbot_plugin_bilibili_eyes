# 调研报告：dsh-see-now 对 B站之眼 / B站之手的可借鉴点

> 调研对象：[SAOS-3624/dsh-see-now](https://github.com/SAOS-3624/dsh-see-now)  
> 调研日期：2026-11-02  
> 调研版本：`0.0.6`（默认分支 `main`）  
> 项目性质：DSH 实时视觉插件，Apache-2.0  
> 调研方式：README、源码、CHANGELOG、测试目录与设计文档  
> 结论先行：**它解决的是“实时看屏幕”而不是“看 B 站视频”，不能直接搬。但它的“按画面变化选帧 + 单进程采帧 + 固定成本拼图 + 可观测调参”非常适合改造进 B站之眼。**

---

## 1. 项目定位

`dsh-see-now` 是给 DSH（DeepSeek Harness）用的实时视觉插件：

- 采集屏幕、摄像头或本地视频；
- 对每一帧计算“画面变化分”；
- 只保留“画面真的变了”的帧；
- 把几帧拼进一张图，作为一次视觉输入；
- 支持常驻观看、阻塞取图、插话、悬浮窗和可选 TTS。

它解决的核心问题是：

> **定时截全屏太贵，隔很久截一张又漏信息。**
> 所以先判断“这一帧值不值得看”，再决定传不传。

它和 B站之眼的共同点只有“把视觉材料压缩后交给模型”，但采集对象、实时性、交互形态完全不同。

## 2. 架构与核心流程

源码主线：

```text
ffmpeg 采集
  → 64×36 低分辨率帧
  → HSV 变化分
  → 切点判定 / 积分取帧 / 静止兜底
  → 与上一张保留帧去重
  → 按密度决定格位档级
  → DP 装箱 / 拼图
  → 一张 PNG + 每帧时间戳/来源
  → 工具结果交给模型
```

关键文件：

| 文件 | 作用 |
| --- | --- |
| [`src/capture.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/capture.js) | 唯一 spawn ffmpeg 的地方，rawvideo 管道 |
| [`src/cuts.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/cuts.js) | 64×36 HSV 变化分 |
| [`src/pipeline.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/pipeline.js) | 帧→打分→切点/积分→留帧→档位→拼图 |
| [`src/tiers.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/tiers.js) | 按帧密度计算每帧格位 |
| [`src/pack.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/pack.js) | 可变尺寸格子的装箱 |
| [`src/runner.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/runner.js) | 采集生命周期、watch/peek/start/stop |
| [`src/loop.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/loop.js) | 常驻循环与自动收工 |
| [`src/binaries.js`](https://github.com/SAOS-3624/dsh-see-now/blob/main/src/binaries.js) | 跨平台查找 ffmpeg |
| [`docs/调参与实测.md`](https://github.com/SAOS-3624/dsh-see-now/blob/main/docs/调参与实测.md) | 参数标定与实测矩阵 |

它的设计原则很清楚：

1. **采集侧自己攒图、自己截断**，模型来取时图已经在队列里；
2. **判定是因果的**，实时场景不使用未来帧；
3. **阈值、档位、唤醒节奏分开**，不把“灵敏度”和“出图频率”混成一个参数；
4. **调试窗独立于发布包**，调参时不污染生产代码。

## 3. 核心机制拆解

### 3.1 变化分：64×36 HSV 加权差

`src/cuts.js` 不做全分辨率比较，而是：

- 把帧降采样到 **64×36 网格**；
- 每格取 4 个采样点求平均；
- 转 HSV；
- 色相按环形距离计算；
- 低饱和像素的色相降权；
- 三通道绝对差求平均，得到 0–255 的分数。

README 给的实测刻度：

| 内容 | 分数 |
| --- | ---: |
| 静止桌面 | 0.00 |
| 光标在静止画面移动 | 0.7 |
| 色调接近的两张照片切换 | 16–18 |
| 滚动网页 / 切窗口 | 30–42 |
| 两张完全不同的照片切换 | 46–63 |

作者还提到一个细节：`ffmpeg scdet` 在同一段测试片上只命中 4/9，而自写 HSV 分数 9/9；原因是 `scdet` 对“同亮度换色”不敏感。

### 3.2 留帧：切点 + 积分 + 兜底

`src/pipeline.js` 的默认值：

```text
cutAbs: 12          // 绝对变化地板
cutSpike: 2.5       // 当前分 > 2.5 × 前后帧
cutMinGap: 0.4s     // 不应期
integralSeconds: 3  // 中等运动攒 3 秒
REF_SCORE: 4        // 中等运动每帧参考分
dupMin: 8           // 与上一张保留帧太像则丢弃
silentFloorSec: 20  // 完全静止也要偶尔给一张
```

两条判据：

**切点**：变化分突然跳高，且相对前后帧是尖峰，并超过绝对地板。  
**积分**：变化分不高但一直有，累加到固定阈值再取一帧。

作者特别强调：**只有尖峰不行，只有地板也不行**。

- 只有尖峰：持续缓慢运动也会被切成一块块；
- 只有地板：一镜到底的视频每帧都差不多，永远不“跳”；
- 所以地板负责“变化够不够大”，尖峰负责“是不是一下子”。

这比简单的“每隔 N 秒取一帧”或“只按热度取帧”更接近“画面信息量”。

### 3.3 档位与拼图：固定成本摊到多帧

`src/tiers.js` 根据“最近窗口内留下了几帧”决定每帧占多大格子：

- 档位 k 的格子边长是 1/k，面积 1/k²；
- 帧密 → 档位高 → 格子小 → 一张图塞更多帧；
- 帧稀 → 档位低 → 格子大 → 一帧更清楚。

`src/pack.js` 用 DP 把不同大小的格子排进方形画布，目标是最大化占用率；`src/sheet.js` 再烧帧号、留缝、合成 PNG。

README 的成本口径：

> 一张图里放 4 帧还是 8 帧，价格一样；  
> 800×450 一张约 233 token（按 DeepSeek-V4 patch 网格估算）。

这就是它愿意“多留一帧”的原因：**漏一帧比多一帧贵**。

### 3.4 watch / peek / 常驻循环

`runner.js` 区分：

- `watch`：阻塞到有图；
- `peek`：立刻取队列里已拼好的图，不重新采集；
- `start` / `stop` / `status`：显式控制生命周期；
- `graceSec`：停采集后保留一段热启动时间；
- `queueDepth`：只保留最近一张，宁可丢老画面，不给模型看十几秒前的事。

`loop.js` 则解决“模型回完一句就不看了”的问题：常驻循环每 2 秒本地判断，有新图才唤醒模型；同时用“连续唤醒无人理会 / 长时间无用户消息”两条线自动收工，避免卡在读图循环里。

### 3.5 “say 是唯一通道”

SeeNow 里普通回复不会进悬浮窗、不会被朗读，只有工具参数 `say` 会。  
所以工具描述反复强调：用户可能在等、在看、刚说话时，把要对用户说的话放进 `say`。

这和 B站之眼“主模型回复由聊天管线发出”的形态不同，但有一个共同教训：

> **工具描述本身要写清楚“什么时候调、结果给谁看、怎么止损”，不能只罗列参数。**

### 3.6 工程化细节

值得记录的工程细节：

- ffmpeg 不走裸命令：`DSH_FFMPEG_PATH` / `FFMPEG_PATH` / `DSH_FFMPEG_DIR` / `$DSH_HOME/tools/ffmpeg/bin` / PATH 逐级查找；
- macOS 没给屏幕录制权限时 ffmpeg 不报错但全黑，插件检测平均像素并提示；
- 主动 `SIGKILL` 时子进程 `code=null`，不能当成失败；
- 调试窗独立在 `debug/`，不进 npm 包；
- 纯函数（`guardReason`、`shouldGoIdle`）单独抽出来测试；
- CHANGELOG 记录“为什么改”，不只记录“改了什么”。

## 4. 与 B站之眼 / B站之手 的对照

| 维度 | dsh-see-now | B站之眼 | 可借鉴程度 |
| --- | --- | --- | --- |
| 输入 | 实时屏幕 / 摄像头 / 本地视频 | 单个 B 站视频 | 中 |
| 选帧 | 画面变化分 + 切点/积分 | 播放热点 + 弹幕 + 字幕 + 均匀 + dHash 去重 | **高** |
| 取帧 | 单 ffmpeg rawvideo 管道 | 每个时间点单独 spawn ffmpeg | **高** |
| 拼图 | 可变档位 + DP 装箱 | 固定网格联系图 / 12 张原图 | 中高 |
| 清晰度 | low/standard/high/ultra 档位 | `frame_height` + 固定帧数 | 中 |
| 实时循环 | 常驻采集 + 唤醒 | 请求驱动，无循环 | 低 |
| 交互 | 悬浮窗、`say`、TTS | AstrBot 聊天/工具 | 低 |
| ASR | 无（语音只做 TTS 事件） | 已有 AstrBot STT ASR | 无直接借鉴 |
| 调试 | 独立调试窗、分数曲线 | `phase0` 脚本、日志 | **高** |
| 工程 | 纯函数、阈值标定、平台抽象 | 已有单测/缓存/线程池 | 中 |

B站之眼现在的取帧逻辑：

1. 弹幕密度找热点；
2. 播放器 view points；
3. 字幕高信息段；
4. 均匀保底；
5. 按 3 秒间隔去重；
6. 对选中时间点逐个 `extract_frames`；
7. 再用 dHash 去重。

优点：不依赖画面分析，快，成本低，适合大多数视频。  
缺点：

- 无法识别“画面本身发生了大变化但弹幕没热度”的段落；
- 固定时间点容易漏掉幻灯片切换、关键演示、突然出现的画面；
- 逐个时间点 spawn ffmpeg，远程流重复连接，慢且容易受风控影响；
- dHash 只能去重，不能判断“这一帧是否值得看”。

SeeNow 的“变化分 + 切点/积分”正好补上第 1、2 点。

## 5. 可借鉴项与优先级

### P0-1：给 B站之眼增加“画面变化选帧”

**目标**：在现有弹幕/字幕/均匀候选之外，增加基于画面变化的候选源，减少“12 帧里一半是同一画面”，同时不漏掉硬切。

**建议做法**：

1. 新增一个离线分析函数，输入视频流/本地临时文件，按 1–2 fps 采样；
2. 每次采样缩到 **64×36**，复用 SeeNow 的 HSV 加权差思路（可重写，不直接复制代码）；
3. 计算：
   - 绝对变化分；
   - 前后帧尖峰；
   - 3 秒积分；
   - 与上一张保留帧的相似度；
4. 输出候选时间点，与现有 `select_timestamps` 的候选取并集；
5. 再做一次“时间间隔去重 + 数量上限”；
6. 高分辨率帧仍然只对最终时间点抽取。

**B站场景的特殊调整**：

- 允许使用“未来帧”，因为视频已经下载/可取流，不需要 SeeNow 的因果约束；
- 阈值不能直接照搬 12：B站有大量镜头运动、转场、字幕动画，需要用一批教程/动画/影视/游戏视频重新标定；
- 保留现有弹幕热点/字幕高信息段作为兜底；
- 增加 `frame_source: "change"` 或 `frame_source: "hybrid"`，默认仍用当前策略，避免一上来改变所有用户体验。

**收益**：

- 幻灯片/教程/游戏实机：更容易抓到“画面切换”；
- 动画/影视：减少同一镜头内的重复帧；
- 在总帧数不变时提高信息密度。

**风险**：

- 画面变化 ≠ 语义变化；镜头运动、闪烁、字幕特效会产生高分；
- 需要调试工具和阈值标定，否则可能比当前更差；
- 离线分析多一次解码，长视频 CPU 成本上升。

### P0-2：把“逐时间点 spawn ffmpeg”改成“一次 ffmpeg 批量抽帧”

当前 `eyes_client.extract_frames()` 对每个时间点执行一次 ffmpeg。  
SeeNow 的采集是**一根 rawvideo 管道**，只启动一次 ffmpeg。

B站视频不需要实时管道，但可以：

- 用一次 ffmpeg，按 `fps=1` 或 `select` 输出低分辨率候选帧；
- 选出最终时间点后，再用一次 ffmpeg 输出高分辨率帧；
- 或直接用 `-vf select='eq(n,...)'` 一次输出所有目标帧。

**收益**：

- 远程流只连接 1–2 次，不是 12 次；
- 减少 ffmpeg 冷启动和网络握手；
- 降低被 B站风控/超时的概率；
- 更容易控制总耗时。

**注意**：

- `select` 的帧号依赖解码顺序，B站视频可能有 VFR，建议用时间戳 `-ss` 窗口或 `fps` 滤镜；
- 需要保留每帧实际时间戳，不要按输出序号猜；
- 失败时回退到现有逐点抽取，保证兼容。

### P0-3：统一 ffmpeg 发现与错误提示

当前 `eyes_client._ffmpeg_exe()` 基本是：

```text
imageio-ffmpeg → "ffmpeg"
```

SeeNow 的 `binaries.js` 更完整：

```text
DSH_FFMPEG_PATH
→ FFMPEG_PATH
→ DSH_FFMPEG_DIR
→ $DSH_HOME/tools/ffmpeg/bin
→ $DSH_HOME/bin
→ PATH
```

建议 B站之眼加一个统一的 `eyes_ffmpeg.py`（或放在 `eyes_client`）：

- 支持用户显式配置 `ffmpeg_path`（之前删过，可以以“可选覆盖”形式重新加回）；
- 支持环境变量；
- 找不到时给出明确安装提示，而不是让 ffmpeg 自己抛 ENOENT；
- 同时供**截帧**和**ASR 抽音频**使用。

这是低风险、直接提升可维护性的改动。

### P1-1：清晰度 / token 档位

SeeNow 的 `quality` 档位：

| 档 | 画布 | 用途 |
| --- | --- | --- |
| low | 800×450 | 看场景/视频，小字不可读 |
| standard | 1066×600 | 中号字 |
| high | 1280×720 | 文件名/小字 |
| ultra | 1600×900 | 真要读字 |

B站之眼目前固定 `frame_height=480`、`frame_count=12`，没有“这次需要看清小字”的升级路径。

建议：

- 增加 `frame_quality: low/standard/high`（或保留 `frame_height`，增加预设）；
- 在 `bilibili_frame` 工具里支持“这一次用高清重截”；
- 用视觉 provider 的实际 token 估算做提示，不直接抄 SeeNow 的 233 token；
- 默认低档，用户明确说“看不清”再升级。

### P1-2：自适应联系图布局

当前联系图是固定 4 列 × 320×180。  
SeeNow 的档位/装箱思路可以简化借用：

- 4 帧：2×2；
- 6 帧：3×2；
- 9 帧：3×3；
- 12 帧：4×3；
- 每格保留时间标签，保持时序。

不建议直接实现 SeeNow 的完整 DP 装箱：它的复杂度来自“任意 1/k 档位 + 实时逐帧追加”，B站之眼一次只有 12 帧，固定候选布局的收益/成本比更高。

### P1-3：调试可视化

SeeNow 的调试窗展示：

- 每一帧的变化分；
- 哪些帧被留下、哪些被丢弃；
- 拼图预览；
- 积分累计与阈值。

B站之眼可以做一个轻量版：

- `phase0/debug_frames.py` 或 `debug_frames.html`；
- 输入一个 BV / 本地视频；
- 输出 CSV/JSON：时间、变化分、候选来源、最终是否入选；
- 生成一张带分数的候选帧总览图。

这比“看日志猜为什么选了这 12 帧”有效得多，也是调阈值的前提。

### P2：工具描述与结果语义

SeeNow 的工具描述明确写了：

- 什么时候用 `watch` / `peek`；
- 不要轮询太快；
- 图是工具结果，不是聊天消息；
- 用户可能看不见普通回复。

B站之眼可以借鉴这种“把成本和行为写进工具描述”的方式：

- `bilibili_watch` 明确“默认 12 帧；只有看不清才调 `bilibili_frame` 高清重截”；
- `bilibili_frame` 说明“只取一个时间点，不要连续调用”；
- 失败时给语义状态，不给原始错误码（已有）。

### P2：纯函数与边界测试

SeeNow 把 `guardReason`、`shouldGoIdle` 这类判断抽成纯函数，单测直接覆盖边界。  
B站之眼可以同样处理：

- 选帧候选合并函数；
- 变化分阈值判断；
- 积分累加；
- 去重；
- 清晰度档位映射。

用合成帧序列测试，不需要真实 B站网络。

## 6. 不建议照搬的内容

1. **实时屏幕采集引擎**  
   `ddagrab` / `gdigrab` / `avfoundation`、屏幕录制权限、平台探测，和 B站视频无关。

2. **常驻循环 / 主动唤醒 / 插话 / 悬浮窗 / TTS**  
   B站之眼是请求驱动，主动循环会带来刷屏和 token 成本；当前不需要。

3. **`cutAbs=12` 等具体阈值**  
   这些值是在“屏幕采集近似无损”的素材上标定的；B站视频有压缩噪声、镜头运动、字幕动画，必须重新标定。

4. **完整 DP 装箱**  
   对 12 帧的固定联系图来说，复杂度大于收益；除非要做“每帧不同大小”的高级布局。

5. **SeeNow 的语音/ASR 部分**  
   `speech.js` 是 TTS 事件总线，不是 ASR。我们的 ASR 已经接了 AstrBot STT，不需要从这里找 ASR 方案。

6. **直接复制源码**  
   项目是 Apache-2.0，允许复用，但需要保留 LICENSE/NOTICE；B站之眼若要保持自己的许可简洁，建议**重写思路**而不是整段拷贝。

## 7. 建议落地路线

### 阶段 A：低成本工程改进（1–2 天）

- 统一 ffmpeg 发现；
- 加“批量抽帧”路径，先不改变选帧结果；
- 用现有测试和真实视频对比耗时/成功率。

**验收**：

- 同一视频抽 12 帧，ffmpeg 启动次数从 12 次降到 1–2 次；
- 截帧结果与旧路径在时间点上一致（允许 ±0.1s）；
- 失败时自动回退旧路径。

### 阶段 B：变化选帧实验（3–5 天）

- 新增离线变化分分析；
- 生成候选时间点，与现有候选合并；
- 加 `frame_source=hybrid` 开关，默认关闭；
- 写调试脚本输出分数与入选原因；
- 用 10–20 个不同品类视频做 A/B。

**验收**：

- 总帧数不变时，重复帧比例下降；
- 关键画面（幻灯片切换、演示结果、突然出现的主体）召回不下降；
- 最坏情况可退回旧策略。

### 阶段 C：体验/成本优化（按需）

- 清晰度档位；
- 自适应联系图；
- 工具描述与“看不清再升级”的交互；
- token 估算与日志。

---

## 8. 风险与边界

- **画面变化不等于内容重要**：镜头运动、转场特效、字幕动画都会产生高分；不能把“变化大”直接等同于“值得看”。
- **B站视频压缩噪声**：低分辨率 HSV 分数可能比屏幕采集更抖，阈值需要重新标定。
- **长视频 CPU 成本**：1–2 fps 全片分析会增加解码开销，必须加时长上限/分段采样/缓存。
- **短片段/静态 PPT**：可能整段没有明显变化，仍需要均匀保底或字幕/弹幕兜底。
- **不同视觉 provider 的 token 计算不同**：不要直接采用 SeeNow 的 233 token 口径。
- **许可证**：借鉴算法思路没问题；如果复制代码，保留 Apache-2.0 LICENSE 与 NOTICE，并确认与 B站之眼当前许可证兼容。

---

## 9. 结论

`dsh-see-now` 最值得借鉴的不是“屏幕采集”，而是它把**“哪些帧值得给模型看”**做成了一条可解释、可调参、可测试的流水线：

1. **变化分**解决“这帧有没有新信息”；
2. **切点 + 积分**解决“硬切”和“持续运动”两种不同场景；
3. **固定成本拼图**解决“多帧几乎不增加成本”；
4. **调试窗和实测矩阵**解决“阈值到底该给多少”。

对应到 B站之眼，优先级建议是：

```text
P0：批量抽帧 + ffmpeg 统一发现
P0/P1：画面变化候选选帧（hybrid，默认关闭）
P1：调试可视化 + 清晰度档位
P2：自适应联系图、工具描述优化
```

不建议改 B站之眼的请求驱动架构，也不建议照搬 SeeNow 的常驻循环、悬浮窗和 TTS。  
**借它的“选帧方法论”和“工程可观测性”，比借它的产品形态更合适。**
